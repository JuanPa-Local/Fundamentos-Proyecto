=========================================================
    OPENLIB MARKET — RESUMEN COMPLETO DEL PROYECTO
=========================================================

1. RESUMEN GENERAL
---------------------------------------------------------
OpenLib Market es una plataforma de compra y descarga de
libros digitales (e-books). Funciona como un marketplace
donde VENDEDORES publican libros, COMPRADORES los buscan,
los agregan al carrito, pagan y los descargan, y un
ADMINISTRADOR modera todo el contenido.

El proyecto se divide en dos partes independientes:

  • BACKEND (Java 21 + Spring Boot 4):
    API REST que maneja toda la lógica de negocio,
    persistencia en PostgreSQL y sesiones en Redis.

  • FRONTEND (HTML + CSS + JavaScript puro):
    Interfaz web estática que consume la API REST.
    No usa frameworks (sin React, Angular, etc.).

Arquitectura: Hexagonal (Puertos y Adaptadores)
  - domain/    → Entidades y reglas de negocio
  - application/ → Casos de uso y fachadas
  - infrastructure/ → Implementaciones técnicas (Redis, JPA)
  - config/    → Configuración de Spring

2.1 RAÍZ Y CONFIGURACIÓN
---------------------------------------------------------

BackendApplication.java

---------------------------------------------------------
2.2 CONFIGURACIÓN (config/)
---------------------------------------------------------

SecurityConfig.java
  → Configura Spring Security. Desactiva CSRF, habilita
    CORS para que el frontend pueda llamar a la API, y
    permite acceso público a todos los endpoints /api/**.

RedisConfig.java
  → Configura la conexión a Redis y el serializador JSON
    para guardar objetos como el carrito de compras.

DataInitializer.java
  → Se ejecuta al arrancar la app. Crea automáticamente
    un usuario administrador por defecto si no existe.

GlobalExceptionHandler.java
  → Captura TODAS las excepciones del backend y las
    convierte en respuestas HTTP con mensajes claros
    (400, 404, 409, 500) en vez de errores genéricos.

2.3 DOMINIO DE USUARIOS (domain/user/)
---------------------------------------------------------

User.java
  → Entidad JPA. Representa un usuario en la base de datos.
    Campos: id, email, passwordHash, fullName, role
    (ADMIN/BUYER/SELLER), active, phone, address, avatarUrl.

UserController.java
  → Endpoints REST para usuarios:
    POST /api/users/register → Registro
    POST /api/users/login    → Inicio de sesión
    GET  /api/users/role/{role} → Listar por rol
    PUT  /api/users/{id}/profile → Editar perfil
    POST /api/users/{id}/activate → Activar cuenta
    POST /api/users/{id}/deactivate → Desactivar cuenta

UserService.java
  → Lógica de negocio de usuarios: valida email único,
    encripta contraseñas con BCrypt, verifica credenciales.

UserRepository.java
  → Interfaz Spring Data JPA. Consultas a la tabla "users":
    buscar por email, listar por rol, verificar existencia.

EXCEPCIONES de usuario:
  CredencialesInvalidasException.java → Login con datos incorrectos
  CuentaInactivaException.java       → Cuenta desactivada por admin
  EmailDuplicadoException.java       → Registro con email repetido
  UsuarioNoEncontradoException.java  → ID de usuario inexistente

---------------------------------------------------------
2.4 DOMINIO DE LIBROS (domain/book/)
---------------------------------------------------------

Book.java
  → Entidad JPA. Representa un libro en la base de datos.
    Campos: id, title, author, description, isbn, price,
    category, status (PENDIENTE/APROBADO/RECHAZADO),
    coverUrl (imagen), filePath (URL del PDF para descarga),
    sellerEmail, downloadCount, averageRating, reviewCount.

BookController.java
  → Endpoints REST para libros:
    GET  /api/books              → Todos los libros
    GET  /api/books/{id}         → Detalle de un libro
    POST /api/books              → Publicar libro (seller)
    GET  /api/books/catalog      → Buscar en catálogo
    GET  /api/books/catalog/filter → Buscar con filtros
    GET  /api/books/categories   → Listar categorías
    GET  /api/books/status/{s}   → Libros por estado
    GET  /api/books/seller/{email} → Libros de un vendedor
    POST /api/books/{id}/approve → Aprobar libro (admin)
    POST /api/books/{id}/reject  → Rechazar libro (admin)
    GET  /api/books/popular      → Libros más populares

BookService.java
  → Lógica de negocio de libros: búsqueda, filtros,
    aprobación/rechazo, validación de ISBN duplicado.

BookRepository.java
  → Interfaz JPA. Consultas avanzadas: búsqueda por
    título/autor, filtrar por categoría+estado, listar
    categorías distintas, ordenar por descargas.

BookObserver.java
  → Patrón Observer. Escucha el evento "OrderCompleted"
    y actualiza automáticamente el contador de descargas
    del libro cuando alguien completa una compra.

Review.java
  → Entidad JPA. Reseña de un libro hecha por un comprador.
    Campos: id, user, book, rating (1-5), comment, status
    (ACTIVA/REPORTADA/OCULTA), createdAt.

ReviewController.java
  → Endpoints REST para reseñas:
    POST /api/reviews            → Crear reseña
    GET  /api/reviews/book/{id}  → Reseñas de un libro
    GET  /api/reviews/reported   → Reseñas reportadas
    POST /api/reviews/{id}/hide  → Ocultar reseña (admin)
    POST /api/reviews/{id}/reactivate → Reactivar reseña

ReviewService.java
  → Lógica: valida que no haya reseña duplicada, actualiza
    el promedio de calificación del libro automáticamente.

ReviewRepository.java
  → Interfaz JPA. Consultas por libro y por estado.

EXCEPCIONES de libros:
  IsbnDuplicadoException.java         → ISBN ya registrado
  LibroNoEncontradoException.java     → Libro inexistente
  LibroNoEnEstadoPendienteException.java → Intentar aprobar uno ya aprobado
  MotivoRechazoObligatorioException.java → Rechazar sin dar razón
  ResenaNoEncontradaException.java     → Reseña inexistente
  ResenaYaExisteException.java         → Usuario ya reseñó ese libro

2.5 DOMINIO DE ÓRDENES Y COMPRAS (domain/order/)

Order.java

OrderController.java

OrderService.java

OrderRepository.java

ItemCarrito.java

CarritoRepository.java

CarritoRestController.java

SesionCheckout.java

DireccionFacturacion.java

MetodoPago.java
  → Enum: TARJETA_CREDITO, PAYPAL, TRANSFERENCIA.

CheckoutSessionGateway.java

CheckoutRestController.java

Favorite.java

FavoriteController.java

    DELETE /api/favorites         → Quitar favorito
    GET    /api/favorites/check   → ¿Es favorito?

FavoriteService.java

FavoriteRepository.java

Biblioteca.java

BibliotecaRepository.java

=========================================================
5. CONFIRMACIÓN: ¿TODOS LOS ARCHIVOS SON NECESARIOS?
=========================================================

SÍ. Cada archivo Java cumple un rol específico:

  • Entidades (Book, User, Order, Review, Favorite):
    Representan las tablas de la base de datos.

  • Controladores (*Controller.java):
    Exponen los endpoints REST que el frontend consume.

  • Servicios (*Service.java):
    Contienen la lógica de negocio (validaciones, reglas).

  • Repositorios (*Repository.java):
    Interfaz para consultar la base de datos (JPA).

  • Fachadas (*Facade.java):
    Coordinan operaciones complejas que involucran
    múltiples servicios (ej: checkout = carrito + orden).

  • Excepciones (exception/*.java):
    Cada una representa un error de negocio específico,
    permitiendo dar mensajes claros al usuario en vez
    de errores genéricos "500 Internal Server Error".

  • Estrategias (strategy/*.java):
    Patrón Strategy para descuentos. Permiten agregar
    nuevos tipos de descuento sin modificar código existente.

  • Infraestructura (infrastructure/*.java):
    Implementaciones técnicas de las interfaces de dominio
    (Redis para carrito, JPA para persistencia, UUID para tokens).

La carpeta "out/" es generada automáticamente por IntelliJ
y NO es parte del código fuente. Puede ignorarse o eliminarse.

8. DOCKERIZACIÓN Y CONTENEDORES (Docker Desktop)
=========================================================

El proyecto está 100% dockerizado usando `docker-compose`.

  1. openlib_postgres (Base de Datos):
     - Imagen: postgres:16
     - Puerto: 5432
     - Guarda los datos de forma persistente.

  2. openlib_redis (Caché y Sesiones):
     - Imagen: redis:7-alpine
     - Puerto: 6379
     - Maneja el carrito de compras en memoria.

  3. openlib_backend (Spring Boot API):
     - Compilado multi-etapa: Usa Maven para compilar y 
       `eclipse-temurin:21-jre-alpine` para ejecutar.
     - Puerto: 8080 (Aquí se envían las peticiones Postman)
     - Se conecta internamente a `db` y `cache`.

  4. openlib_frontend (Servidor Web Estático):
     - Imagen: nginx:alpine
     - Puerto: 80 (Acceso vía http://localhost)
     - Sirve los archivos HTML/JS/CSS de forma ultrarrápida.

Para ver que todo está bien en Docker Desktop:
- Ve a la pestaña "Containers".
- Deberías ver un grupo llamado "openlib market" (o similar
  según el nombre de la carpeta).
- Al expandirlo, deben aparecer los 4 contenedores en verde (Running).
- Si revisas los logs de "openlib_backend", deberías ver
  el logo de Spring Boot y el mensaje "Started BackendApplication".

10. CORRECCIONES RECIENTES Y APLICACIÓN DE PRINCIPIOS SOLID
=========================================================

Durante el último ciclo de desarrollo se detectaron y corrigieron problemas críticos en los flujos principales. Se detallan a continuación las rutas de los archivos, la lógica ejecutada y los patrones de diseño aplicados para cumplir con la Arquitectura Limpia (Clean Architecture) y SOLID:

A. Flujo de Compra y Carrito (NullPointerExceptions)
- Ubicación de la Lógica: 
  - Frontend: `frontend/js/cart.js` (Método `processCheckout()`)
  - Backend: `backend/src/main/java/com/openlib/backend/domain/order/OrderController.java` (Método `createOrder()`) y `ItemCarrito.java`.
- Lógica de Ejecución: Al momento de confirmar la compra, el cliente itera sobre los elementos en Redis (`CarritoFacade`) y envía una petición POST por cada libro a `/api/orders`. El problema radicaba en que el objeto DTO `ItemCarrito` nombraba su atributo como `libroId`, pero el frontend intentaba inyectar un valor bajo un identificador equivocado al JSON, enviando un valor nulo al controlador.
- Patrones y SOLID:
  - Principio de Responsabilidad Única (SRP): Se programó defensivamente el controlador (`OrderController`) en la capa de presentación para que capture ausencias de atributos e identifique campos nulos en variables nativas (como `UUID.fromString`), respondiendo con un `400 Bad Request` semántico. La responsabilidad de la creación de la orden sigue fuertemente encapsulada en el servicio de negocio `OrderService.java`.
  - Patrón Facade (Simulado): En el cliente (`cart.js`), se consolida la interacción de vaciar el carrito y crear órdenes de manera secuencial sin exponer esa complejidad al usuario final.

B. Creación de Reseñas y Contadores Vacíos (NPE)
- Ubicación de la Lógica:
  - Backend: `backend/src/main/java/com/openlib/backend/domain/book/Book.java` (Método `actualizarCalificacion()`) y `BookObserver.java` (Método `onOrderCompleted()`).
  - Frontend: `frontend/js/buyer.js` (Métodos `submitLibraryReview()` y `openLibraryReviewModal()`).
- Lógica de Ejecución:
  1. Reseñas: Un usuario envía un POST a `/api/reviews`. El `ReviewController` lo capta, transfiere el payload al `ReviewService` que guarda la reseña, recupera la entidad Libro y llama a `book.actualizarCalificacion(rating)`.
  2. Programación Defensiva en el Modelo Rico (Rich Domain): Al procesar compras o reseñas en libros antiguos, las propiedades primitivas como `averageRating` o `downloadCount` estaban nulas en la base de datos (por falta de inicialización previa). Desempaquetarlas a tipos crudos (`Double`/`int`) disparaba excepciones `NullPointerException`. Se agregaron verificaciones `!= null` directamente dentro de las operaciones lógicas de `Book.java`, garantizando un estado interno válido (`fallback` a 0 o 0.0) antes de efectuar matemáticas.
  3. Actualización de Interfaz Reactiva: En `buyer.js`, en cuanto la reseña tiene éxito vía POST, se manda a llamar a `loadLibrary()` dinámicamente. Esto manipula el DOM para eliminar el botón de 'Reseñar' en vivo e inyectar un indicador "✔ Reseñado", otorgando una experiencia fluida.
- Patrones y SOLID:
  - Patrón Observer (Event-Driven): Cuando se completa una compra en `OrderService`, no se invoca directamente al `BookService` (lo que generaría un altísimo y no deseado acoplamiento). En vez de ello, se emite un `OrderCompletedEvent`. `BookObserver` intercepta el evento e incrementa silenciosamente el contador de descargas del libro en cuestión.
  - Principio Abierto/Cerrado (OCP): Dado el enfoque guiado por eventos, el flujo de compra principal está "abierto a extensiones, cerrado a modificaciones". Añadir notificaciones futuras (ej. correo post-compra) requerirá tan sólo agregar nuevos *Observers*, sin alterar `OrderService`.

C. Eliminación de Libros (Restricciones Foreign Key en Vendedor)
- Ubicación de la Lógica:
  - Backend: `backend/src/main/java/com/openlib/backend/domain/book/BookService.java` (Método `deleteBook()`).
  - Repositorios inyectados: `FavoriteRepository.java`, `ReviewRepository.java`, `OrderRepository.java`.
- Lógica de Ejecución: Los vendedores (Rol `SELLER`) se topaban con un error "500 Internal Server Error" en producción al intentar usar el endpoint `DELETE /api/books/{id}`. La Base de Datos Relacional de Postgres bloqueaba la instrucción `bookRepository.deleteById(id)` porque el libro ya estaba presente como una Llave Foránea ("Foreign Key") activa en tablas transaccionales u opcionales (Reseñas, Favoritos, Órdenes Históricas).
  Se corrigió orquestando un procedimiento de limpieza integral transaccional (etiquetado explícitamente con `@Transactional` en `BookService`):
  1. Búsqueda y destrucción de favoritos huérfanos (`favoriteRepository.findByBookId(id)`).
  2. Eliminación de reseñas asociadas (`reviewRepository.deleteAll(...)`).
  3. Modificación del historial: Las compras no se destruyen para preservar la contabilidad y biblioteca del comprador, pero sí se nulifica el registro hacia el libro físico (`order.setBook(null)`).
  4. La eliminación del objeto raíz se procesa exitosamente.
- Patrones y SOLID:
  - Principio de Inversión de Dependencias (DIP): Se refactorizó el `BookService` para inyectar por constructor al `FavoriteRepository`. El servicio de casos de uso nunca toca tecnología ni dialectos SQL directamente, dependiendo de abstracciones estables de alto nivel originadas en Spring Data.
  - Segregación de Interfaces (ISP): Se respetó al crear métodos discretos y de firma explícita, tales como `findByBookId()`, sobre la interfaz general `FavoriteRepository`, ofreciendo gran modularidad.

CONCLUSIÓN ARQUITECTÓNICA GLOBAL (CLEAN ARCHITECTURE)
El proyecto demuestra apego y rigurosidad al patrón de Capas Centralizadas / Hexagonal:
- Capa de Dominio (Entities): Las clases como `Book` no son simples "Data Bags" (Anemic Domain), sino entidades maduras con métodos (`actualizarCalificacion`) y control de invariantes que repelen inconsistencias.
- Capa de Aplicación (Use Cases/Services): Gestores de transacción (`BookService`, `OrderService`, Observers y Facades) que se orquestan bajo una lógica limpia y desacoplada de la web.
- Capa de Infraestructura y Presentación (Adapters): Controladores HTTP y Repositorios JPA Spring Boot, aislando a las librerías nativas del centro del sistema. El Frontend consume todo exclusivamente a través de la API Asincrónica (Fetch JSON / RESTFul) desde una naturaleza Single Page Application (SPA), garantizando máxima escalabilidad.
